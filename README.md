# ระบบจัดการสต็อกอุปกรณ์ไอที (Hardware Stock Management System)

ระบบบริหารคลังอุปกรณ์ไอทีแบบครบวงจร ทดแทนการบันทึกด้วยไฟล์ Excel รายเดือน
รองรับ **หลายคลัง (MMT / MTHAI)** ดูข้อมูลแยกรายคลังและดูรวมทุกคลังได้,
**การรับอุปกรณ์เข้า (IN)**, **การเบิกออก (OUT)**, **การรับคืน**, **การโอนย้ายระหว่างคลัง**,
**การปรับปรุงสต็อก**, การติดตามทรัพย์สินรายชิ้นด้วย Serial และรายงานรูปแบบเดียวกับไฟล์เดิม

---

## คุณสมบัติหลัก

### 🏬 ระบบหลายคลัง — ดูแยกและดูรวม
ระบบติดตั้งมาพร้อมคลัง **MMT** และ **MTHAI** (เพิ่ม/แก้ไข/ปิดใช้งานได้เองที่หน้าข้อมูลหลัก)

- **ตัวเลือกคลังอยู่บนแถบด้านบนของทุกหน้า** เลือกได้ว่าจะดู *ทุกคลัง (รวม)* หรือเจาะเฉพาะคลังใดคลังหนึ่ง
  ระบบจำค่าที่เลือกไว้ข้ามหน้าและข้ามการเข้าใช้งานครั้งถัดไป
- **หน้ายอดคงเหลือปรับตัวเอง 2 โหมด**
  - เลือก *ทุกคลัง* → ตารางเปรียบเทียบ `อุปกรณ์ | คลัง MMT | คลัง MTHAI | รวมทุกคลัง`
  - เลือกคลังใดคลังหนึ่ง → ตารางรายละเอียดเฉพาะคลังนั้น พร้อมยอดรับเข้า/จ่ายออก/Serial ของคลังนั้น
- **ทุกเอกสารผูกกับคลัง** — รับเข้า เบิกออก รับคืน และปรับปรุง ต้องระบุคลังเสมอ
- **สต็อกแยกขาดจากกันจริง** — เบิกเกินยอดของคลังนั้นไม่ได้ แม้ยอดรวมทุกคลังจะพอ
- **Serial รู้ว่าอยู่คลังไหน** — เบิก Serial ข้ามคลังไม่ได้ ระบบจะบอกให้โอนย้ายก่อน
- ทุกรายงานและ CSV กรองตามคลังได้ หรือดูรวมทุกคลัง

### 🔁 โอนย้ายระหว่างคลัง
- ตัดยอดออกจากคลังต้นทางและเพิ่มเข้าคลังปลายทางในเอกสารเดียว (`TR-2569-0001`)
- ยอดรวมทุกคลังไม่เปลี่ยน — เปลี่ยนแค่ว่าของอยู่ที่ไหน
- โอน Serial ได้ ระบบจะย้ายทะเบียนทรัพย์สินไปคลังปลายทางให้อัตโนมัติ
- ยกเลิกใบโอนได้ ยอดและคลังของ Serial จะย้อนกลับทั้งคู่

### 📥 รับอุปกรณ์เข้าคลัง
- บันทึก วันที่รับ, เลขที่ PO, ผู้ขาย, รายการอุปกรณ์ และราคาต่อหน่วย
- อุปกรณ์ที่ติดตามรายชิ้น กรอก Serial ได้ทีละหลายรายการ ระบบ**นับจำนวนให้อัตโนมัติ**
  จึงไม่มีทางที่จำนวนกับ Serial จะไม่ตรงกัน
- เลขที่เอกสารออกอัตโนมัติ `IN-2569-0001` แยกตามปี

### 📤 เบิกอุปกรณ์ออก
- บันทึกครบตามไฟล์เดิม: วันที่, ผู้เบิก (รหัส - ชื่อ / แผนก), Desktop / Laptop / Accessories,
  เจ้าหน้าที่ IS, สถานะ Charge (Y/N) และ Remark
- เลือก Serial จาก**เฉพาะของที่มีอยู่ในคลังจริง** — เบิกซ้ำหรือเบิกของที่ถูกเบิกไปแล้วไม่ได้
- ตรวจยอดคงเหลือก่อนบันทึกเสมอ เบิกเกินสต็อกระบบจะปฏิเสธพร้อมบอกยอดที่เหลือจริง

### ↩️ รับคืนอุปกรณ์
- เลือกผู้คืนแล้วระบบกรอง Serial ที่บุคคลนั้นถือครองอยู่มาให้
- แยกสภาพ **ใช้งานได้** (คืนเข้าคลัง เพิ่มยอด) กับ **ชำรุด** (ตัดจำหน่าย ไม่เพิ่มยอด)

### ⚖️ ปรับปรุงสต็อก
- ใช้บันทึกผลการตรวจนับ ของหาย ของเกิน พร้อมแสดงยอดใหม่ให้เห็นก่อนบันทึก
- ระบบไม่ยอมให้ปรับจนยอดติดลบ

### 🔎 ระบบเช็คข้อมูลคลัง
- ยอดคงเหลือพร้อมตัวกรอง (หมวดหมู่, ใกล้หมด, หมดคลัง, มีของ) และการเรียงลำดับ
- **การ์ดสต็อก** รายอุปกรณ์ แสดงยอดสะสม (running balance) ทุกการเคลื่อนไหว
- **ทะเบียนทรัพย์สิน** ค้นหาได้ว่า Serial ไหนอยู่ที่ใคร แผนกอะไร พร้อม**ไทม์ไลน์**ทั้งชีวิตของอุปกรณ์ชิ้นนั้น
- แจ้งเตือนของใกล้หมดบนเมนูและแดชบอร์ด

### 📈 รายงาน
| รายงาน | รายละเอียด |
|---|---|
| รายเดือน (รูปแบบเดิม) | ตาราง IN และ OUT หน้าตาเดียวกับไฟล์ Excel เดิม แยกคอลัมน์ Desktop / Laptop / Accessories พร้อมคอลัมน์คลัง |
| ยอดคงเหลือแยกรายคลัง | ตารางเปรียบเทียบทุกคลังพร้อมยอดรวม (`/api/stock/by-warehouse`) |
| สรุปตามแผนก | จำนวนใบเบิก จำนวนชิ้น มูลค่า แยก Charge Y/N |
| สรุปตามหมวดหมู่ | รับเข้า จ่ายออก คงเหลือ และมูลค่า |
| อุปกรณ์ที่เบิกบ่อย | จัดอันดับอุปกรณ์ที่ถูกเบิกมากที่สุด |
| ทรัพย์สินที่ถือครอง | พนักงานแต่ละคนถืออุปกรณ์อะไรอยู่บ้าง |
| สรุปค่าใช้จ่าย | มูลค่าที่ต้องเรียกเก็บ (Charge = Y) แยกตามแผนก |
| บันทึกการใช้งาน | ใครทำอะไรกับระบบเมื่อไหร่ |

ทุกรายงานส่งออก **CSV พร้อม BOM** เปิดใน Excel แล้วภาษาไทยไม่เพี้ยน และสั่งพิมพ์ได้

### 🔐 ผู้ใช้งานและสิทธิ์
| สิทธิ์ | ทำอะไรได้ |
|---|---|
| `admin` ผู้ดูแลระบบ | ทุกอย่าง รวมถึงจัดการผู้ใช้และลบข้อมูลหลัก |
| `officer` เจ้าหน้าที่คลัง | บันทึก/ยกเลิกเอกสาร และเพิ่มแก้ไขข้อมูลหลัก |
| `viewer` ผู้ดูข้อมูล | ดูข้อมูลและรายงานอย่างเดียว |

รหัสผ่านเข้ารหัสด้วย `scrypt` เซสชันเป็น signed cookie (HttpOnly) และมีบันทึก audit log

## ฐานข้อมูล

ระบบใช้ **MySQL / MariaDB** เซิร์ฟเวอร์เดียวกับโปรเจกต์อื่นในองค์กร
ฐานข้อมูลของระบบนี้ชื่อ **`Stock-MC`** (ชื่อมีขีดกลาง เวลาเขียน SQL เองต้องครอบด้วย backtick เสมอ เช่น ``USE `Stock-MC`;``)

ตั้งค่าผ่านไฟล์ `config.ini` ที่อยู่ข้าง `package.json` — รูปแบบเดียวกับโปรเจกต์อื่น
ไฟล์นี้ไม่ถูก track ใน git เพราะมีรหัสผ่าน (ดูตัวอย่างที่ `config.ini.example`)

```ini
[database]
host = 127.0.0.1
port = 3306
user = stock_app
password = ••••••••
name = Stock-MC
pool_size = 8

[server]
port = 3000
https = false

[session]
secret = ค่าสุ่มยาว ๆ

[setup]
admin_password = admin1234
```

ทุกค่ากำหนดทับด้วย environment variable ได้ (`DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`,
`DB_NAME`, `PORT`, `SESSION_SECRET`, `ADMIN_PASSWORD`) สะดวกเวลารันใน container

## เริ่มใช้งาน

วิธีที่ง่ายที่สุดคือใช้ตัวช่วยติดตั้ง ซึ่งจะถามค่าที่จำเป็น สร้าง `config.ini`
สร้างฐานข้อมูลกับผู้ใช้ให้ (ถ้าให้รหัส root) แล้วสร้างตารางและผู้ดูแลระบบให้เสร็จในขั้นตอนเดียว

```bash
npm install
npm run setup        # ตัวช่วยติดตั้งแบบถาม-ตอบ
npm start            # เปิดเซิร์ฟเวอร์ที่ http://localhost:3000
```

ถ้าต้องการตั้งค่าเอง: คัดลอก `config.ini.example` เป็น `config.ini` แก้ค่าให้ตรงกับเซิร์ฟเวอร์จริง
แล้วสร้างฐานข้อมูลกับสิทธิ์ให้ผู้ใช้แอปก่อน

```sql
CREATE DATABASE `Stock-MC` CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'stock_app'@'localhost' IDENTIFIED BY 'รหัสผ่านของคุณ';
GRANT ALL PRIVILEGES ON `Stock-MC`.* TO 'stock_app'@'localhost';
```

จากนั้นสั่ง `npm run seed` เพื่อสร้างตารางและผู้ดูแลระบบ
ตารางจะถูกสร้าง/ปรับปรุงอัตโนมัติทุกครั้งที่เปิดเซิร์ฟเวอร์ จึงไม่ต้องรัน migration แยก

ต้องการข้อมูลตัวอย่างสำหรับทดลอง (อ้างอิงจากไฟล์ HARDWARE REQUEST 2026):

```bash
npm run seed:demo    # เพิ่มข้อมูลตัวอย่าง
npm run reset        # ล้างข้อมูลทุกตารางแล้วสร้างใหม่พร้อมข้อมูลตัวอย่าง
```

**บัญชีเริ่มต้น** — ผู้ใช้ `admin` รหัสผ่าน `admin1234` (⚠️ เปลี่ยนทันทีหลังเข้าใช้งานครั้งแรก ผ่านปุ่ม 🔑 มุมขวาบน)

### ทดสอบระบบ

```bash
npm test             # ชุดทดสอบ 60 รายการ (ตรรกะสต็อก + หลายคลัง + API)
```

ชุดทดสอบต่อกับ MySQL จริง โดยแต่ละไฟล์ทดสอบใช้ฐานข้อมูลของตัวเอง
(`Stock-MC-test-<ชื่อไฟล์>`) และล้างข้อมูลก่อนทุกเคส จึงไม่กระทบฐานข้อมูลใช้งานจริง
ผู้ใช้ฐานข้อมูลต้องมีสิทธิ์สร้างฐานข้อมูลที่ขึ้นต้นด้วย `Stock-MC-test-`

```sql
GRANT ALL PRIVILEGES ON `Stock-MC-test-%`.* TO 'stock_app'@'localhost';
```

## หลักการออกแบบที่ควรรู้

**ยอดคงเหลือคำนวณจากบัญชีเดินสต็อก (ledger) เสมอ**
ตาราง `stock_moves` บันทึกทุกการเคลื่อนไหวเป็นค่าบวก/ลบ ยอดคงเหลือ = ผลรวมของรายการทั้งหมด
ไม่มีการเก็บตัวเลขคงเหลือไว้ซ้ำในที่อื่น ยอดจึงไม่มีทางเพี้ยนจากกัน

**การยกเลิกเอกสารใช้วิธีกลับรายการ ไม่ใช่การลบ**
เอกสารที่ยกเลิกยังอยู่ในระบบพร้อมเหตุผลและผู้ยกเลิก ระบบจะสร้างรายการกลับทางให้
และคืนสถานะ Serial กลับเป็นค่าก่อนหน้าโดยอ้างอิงจากตาราง `serial_events`
หากมีเอกสารอื่นทำต่อจากเอกสารนั้นแล้ว ระบบจะปฏิเสธพร้อมบอกว่าต้องยกเลิกใบไหนก่อน

**ทุกการบันทึกอยู่ใน transaction เดียว**
ถ้ามีบรรทัดใดผิดพลาด ทั้งเอกสารจะไม่ถูกบันทึกเลย ไม่มีเอกสารค้างครึ่ง ๆ กลาง ๆ

**เลขที่เอกสารกันชนกันด้วยคีย์ UNIQUE และการลองใหม่อัตโนมัติ**
เลขที่เอกสารสร้างจากเลขล่าสุด + 1 หากผู้ใช้สองคนบันทึกพร้อมกัน คีย์ UNIQUE จะกันข้อมูลซ้ำไว้
และระบบจะลองออกเลขใหม่ให้เองโดยผู้ใช้ไม่เห็นข้อผิดพลาด

**ของชำรุดที่รับคืนจะไม่ถูกนับกลับเข้าคลัง**
บันทึกไว้ในใบรับคืนและเปลี่ยนสถานะ Serial เป็น "ตัดจำหน่าย" แต่ไม่เพิ่มยอดคงเหลือ

**ทุกรายการเดินสต็อกผูกกับคลังหนึ่งคลังเสมอ**
ยอดรายคลังคือผลรวมของรายการในคลังนั้น ส่วนยอดรวมคือผลรวมทุกคลัง — ทั้งสองค่าจึงมาจากแหล่งเดียวกัน
ไม่มีการเก็บยอดสรุปแยกไว้ที่อื่น การโอนย้ายจึงเป็นเพียงการบันทึก 2 รายการ (ออกจากต้นทาง + เข้าปลายทาง)

**จุดสั่งซื้อขั้นต่ำกำหนดที่ระดับอุปกรณ์ ไม่ใช่ระดับคลัง**
การแจ้งเตือน "ใกล้หมด" จึงคิดจากยอดรวมทุกคลัง ซึ่งตรงกับมุมมองของการจัดซื้อ

## API หลัก

ทุก endpoint อยู่ใต้ `/api` และต้องเข้าสู่ระบบก่อน (ยกเว้น `/api/health` และ `/api/auth/login`)

| Method | Endpoint | หน้าที่ |
|---|---|---|
| `POST` | `/auth/login`, `/auth/logout`, `/auth/change-password` | จัดการเซสชัน |
| `GET/POST/PUT/DELETE` | `/warehouses`, `/items`, `/categories`, `/departments`, `/employees`, `/is-staff`, `/suppliers` | ข้อมูลหลัก |
| `GET/POST` | `/receipts`, `/issues`, `/returns`, `/adjustments`, `/transfers` | เอกสาร |
| `POST` | `/{เอกสาร}/:id/void` | ยกเลิกเอกสาร |
| `GET` | `/stock/by-warehouse` | ยอดแยกรายคลังพร้อมยอดรวมในตารางเดียว |
| `GET` | `/stock/balance`, `/stock/low`, `/stock/moves`, `/stock/card/:itemId` | ข้อมูลคลัง |
| `GET` | `/serials`, `/serials/:id` | ทะเบียนทรัพย์สินและไทม์ไลน์ |
| `GET` | `/reports/monthly`, `/reports/by-department`, `/reports/assets-by-holder`, … | รายงาน |
| `GET` | `/dashboard` | ข้อมูลสรุปหน้าแรก |

เพิ่ม `.csv` ต่อท้าย endpoint ของรายงานเพื่อดาวน์โหลดเป็นไฟล์ เช่น `/api/stock/balance.csv`

ทุก endpoint ที่เกี่ยวกับสต็อกและรายงานรับพารามิเตอร์ `warehouse_id` เพื่อเจาะดูรายคลัง
**ถ้าไม่ส่งพารามิเตอร์นี้ = ดูรวมทุกคลัง**

## การนำขึ้นใช้งานจริง

1. ตั้ง `secret` ในหัวข้อ `[session]` เป็นค่าสุ่มที่ยาวพอ (`npm run setup` สุ่มให้อัตโนมัติ)
2. ตั้ง `https = true` ในหัวข้อ `[server]` เมื่อให้บริการผ่าน HTTPS หรือ reverse proxy ที่เป็น HTTPS
   แล้วคุกกี้จะตั้ง flag `Secure` ให้เอง
3. สำรองฐานข้อมูลเป็นประจำ เช่น
   ```bash
   mysqldump --single-transaction --default-character-set=utf8mb4 'Stock-MC' > stock-mc-$(date +%F).sql
   ```
4. เปลี่ยนรหัสผ่าน `admin` และสร้างบัญชีแยกให้ผู้ใช้แต่ละคนเพื่อให้ audit log มีความหมาย
5. ตรวจสอบรายชื่อคลังที่หน้า **ข้อมูลหลัก → คลังสินค้า** ให้ตรงกับหน้างานจริงก่อนเริ่มคีย์ข้อมูล

### อัปเกรดจากเวอร์ชันก่อนหน้า

เปิดเซิร์ฟเวอร์ตามปกติ ระบบจะสร้างตารางที่ยังไม่มีและปรับโครงสร้างเดิมให้เองโดยอัตโนมัติ
(เช่น เพิ่มคอลัมน์คลังแล้วย้ายข้อมูลเดิมเข้าคลังแรก) — ไม่มีข้อมูลสูญหาย
แนะนำให้ `mysqldump` สำรองไว้ก่อนอัปเกรดตามปกติ

> **หมายเหตุ:** เวอร์ชันแรกสุดของระบบใช้ SQLite (ไฟล์ `data/stock.db`) ตั้งแต่เวอร์ชันนี้เป็นต้นไป
> ย้ายมาใช้ MySQL เซิร์ฟเวอร์เดียวกับโปรเจกต์อื่นแล้ว หากมีข้อมูลค้างอยู่ในไฟล์ SQLite เดิม
> ต้องย้ายข้อมูลเอง (ระบบไม่ได้แปลงให้อัตโนมัติ เพราะเป็นคนละเครื่องยนต์ฐานข้อมูล)

ระบบไม่เรียกใช้ทรัพยากรภายนอกใด ๆ จึงใช้งานในเครือข่ายปิด (ไม่มีอินเทอร์เน็ต) ได้ทันที
